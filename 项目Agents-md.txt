## 推荐目录结构

如无特殊情况，优先采用以下目录结构：

- `pages/`：页面
- `components/`：通用组件
- `utils/`：工具函数
- `services/`：接口请求与业务 API
- `store/`：全局状态
- `assets/`：图片、图标等静态资源
- `config/`：配置文件
- `docs/`：项目阶段文档
- `app.js`：小程序入口逻辑
- `app.json`：小程序全局配置
- `app.wxss`：全局样式

如果项目已有目录结构，优先遵循现有结构，不要随意重构。

## 开发规则

1. 开发前先阅读 `AGENTS.md` 和 `docs/` 中已有文档。
2. 不要一上来直接写代码，必须先确认当前阶段。
3. 优先完成 MVP 功能，不要主动扩展非 MVP 功能。
4. 修改代码时保持最小改动，避免影响无关功能。
5. 优先复用已有组件、工具函数和样式。
6. 可复用 UI 应抽成组件。
7. 网络请求必须统一封装在 `services/` 中。
8. 通用工具函数必须放在 `utils/` 中。
9. 常量、枚举、配置项不要散落在页面文件中。
10. 不要删除已有功能，除非任务明确要求。

## UI 与交互规则

1. 页面应简洁、清晰，适合移动端使用。
2. 所有核心操作都要有反馈。
3. 必须处理加载中、空状态、错误状态。
4. 表单提交前必须做基础校验。
5. 用户操作失败时要给出友好提示。
6. 不要让页面长时间无响应。
7. 样式应保持统一，不要每个页面各写一套风格。

## 微信能力规则

1. 权限申请必须在用户触发相关功能时进行。
2. 不要一进入页面就申请相机、相册、定位等权限。
3. 订阅消息必须由用户主动触发授权。
4. 使用微信登录、手机号、支付等能力时，要遵守微信规范。
5. 不要收集与当前功能无关的用户信息。

## AI 功能规则

如果本项目包含 AI 能力，必须遵守：

1. 不要在小程序前端直接调用大模型 API。
2. API Key 必须放在后端、云函数或安全服务中。
3. 用户输入和 AI 输出都应做内容安全处理。
4. AI 输出尽量使用结构化格式，方便程序解析。
5. 关键结果必须允许用户确认或修改。
6. 必须处理 AI 请求失败、超时、空结果等情况。
7. 必须控制调用频率和成本。

如果本项目暂不包含 AI，不要主动添加 AI 功能。

## 安全与隐私

1. 不要提交密钥、密码、Token、私有接口地址。
2. 不要把敏感信息写死在前端代码中。
3. 不要在日志中输出用户隐私数据。
4. 用户数据只用于当前功能目的。
5. 涉及个人信息时，应遵守隐私政策和微信平台要求。

## 测试要求

开发完成后必须检查：

1. 核心流程是否可以完整走通。
2. 页面跳转是否正常。
3. 表单校验是否有效。
4. 加载、空状态、错误状态是否完整。
5. 接口失败、无网络、无数据时是否可用。
6. 不同屏幕尺寸下是否有明显样式问题。
7. 是否遗留调试代码、无用变量、敏感信息。
8. 是否更新了对应阶段文档。

测试结论必须写入 `docs/05-test-report.md`。

## AGENTS.md 更新规则

开发过程中可以更新本文件，但只能写入长期有效的项目规则。

适合写入本文件的内容：

1. 项目定位变化。
2. MVP 范围变化。
3. 稳定下来的目录结构。
4. 稳定下来的数据模型。
5. 长期使用的技术方案。
6. Codex 反复犯错后需要固定下来的规则。

不适合写入本文件的内容：

1. 临时待办。
2. 某一次开发任务的细节。
3. 还没确认的想法。
4. 个人备忘。
5. 已经过期的开发记录。

临时内容应写入 `docs/04-development-log.md`。
